Why it fails

IN ONE SENTENCE

Of 565 failures, about half are hidden-test failures where the agent never ran a testbench, a quarter are interface mismatches with names the hidden testbench uses, and when the agent did test its own work, its testbench passed on code the hidden tests failed 61 times out of 73.

Every failed problem-run in M3's 14 runs gets one label: the first of a fixed list of rules that holds, read from the harness's per-test log, the agent's trace and its summary. The rules are in tools/taxonomy.py; no model is involved.

The interface story: a handle the agent was never given

Two labels are interface failures: the hidden build failed on code that compiled for the agent (74 failures, on 8 problems), or the hidden testbench reached for a port, signal, instance or parameter by a name the design does not have (73 failures, on 9 problems). The agent cannot see either from its own checks, because the names are only in the hidden testbench.

Self-check passed, hidden tests failed: 61 of 73

When a submission failed and the agent had run its own testbench on it, the last run of that testbench had passed in 61 of the 73 cases. Its testbenches check less than the hidden ones. These 61 failures are spread over 26 problems.

73 failed submissions with an own-testbench run · top: own testbench (blue = passed, ochre = failed) · bottom: hidden tests (hatched = failed)M3, 14 runs
Each pair is one failed problem-run: the upper segment is the agent's own testbench, the lower one the hidden tests.
WHYWhy deterministic rules plus hand labels, with a separate hold-out set

Rules give every failure exactly one label by a fixed precedence, from logs and traces, the same way every time, so anyone can rerun them on the committed CSVs. Hand labels check whether the rules say what a person reading the log would say. The rule-development set (15 real failures) found that the earlier rules missed name mismatches: they agreed on 12 of 15, the misses led to the signal_missing_hidden rule, and with it they agree on 15 of 15. Because that set shaped the rule, it cannot score it. So a hold-out set of 15 other failures was drawn after the rule was fixed (seed 20261024): 15 of 15 agree. It contains no signal_missing_hidden case, so the new rule is checked only on the development set, and the same person wrote both the labels and the rule.

Read as a verification engineer would

IN ONE SENTENCE

The agent's self-check is a testbench with no coverage and no quality measure, which is why it passed on code the hidden tests failed in 61 of 73 cases; the planned M3c milestone answers that with a mutation-score gate on the agent's testbench and an interface diff by elaboration.

The hidden cocotb tests play the role of a sign-off regression the designer cannot see. The agent's own testbench plays the designer's unit test. Mapped onto the usual verification concepts, here is what the project does and does not do.

ConceptWhat this project doesWhat it does not doStatus
Reference model and scoreboard The hidden tests compare the design with a model; a DES failure reads DUT o_data does not match model o_data. The harness's pass or fail is the only score. The agent's own testbenches are not inspected for whether they have a model; that is not measured. HIDDEN TESTS ONLY
Coverage Nothing measured. The 61-of-73 result is the symptom: a testbench that passes on wrong code did not exercise what the hidden tests exercise. No code or functional coverage on the agent's testbench. The M5 track plans functional coverage in cocotb. NOT MEASURED
Testbench quality Measured indirectly, from outcomes: the own testbench passed in 61 of 73 failed submissions where it ran (84% false passes on those). No direct measure yet. M3c plans a mutation score: does the agent's testbench catch deliberately broken copies of its own design? INDIRECT
Constrained-random stimulus Not asked of the agent; its prompt lists the checks it may run. No constrained-random generation and no seed sweep of stimulus. NOT DONE
Assertions (SVA) None. Static checks are Verilator lint and a Yosys read and synth. No SVA. The M5 track plans SVA properties checked with SymbiYosys. PLANNED (M5)
Formal: BMC, equivalence, mutation None run yet. Planned for M3c: a mutation-score gate on the agent's testbench (Yosys mutate) and an interface diff by elaboration (pyslang), both fixed steps in the graph. Formal checks of SVA properties with SymbiYosys are planned for the M5 track. No equivalence checking is planned. PLANNED
Regression triage Done: a deterministic label for each of 565 failures, checked against hand labels; a measured noise floor (flaky results: 10 problems flip between identical runs); a null-agent floor and a golden check (M0). The hidden build's own compiler message is not in the log, so the cause of each compile_fail_hidden is not shown one by one. DONE

The two M3 failure modes have verification answers. A testbench that passes on wrong code is a testbench-quality and coverage problem: a mutation score asks whether the testbench fails on mutated copies of the design, and so measures what it can catch. A name the hidden testbench needs but the design lacks is an interface problem: elaborating the design and diffing its ports, parameters and hierarchy against the specification catches it before submission, when the name is given. Neither has results yet.

How this compares with others

IN ONE SENTENCE

Three published rows use exactly these 92 problems in the same release, and they land in the same range as ours (48 to 53 of 92 against our 41 to 56); everything else published on CVDP uses other problems, other modes or commercial tools, and is context only.

Every number here was checked against its primary source on 24 October 2026. Our runs use only the free, open-tool split (92 problems, four categories), specific models, one run per setting in M2 and pass@1 from a single sample.

COMPARABLE Same 92 problems (agentic_code_generation_no_commercial), same release 1.1.0

Why these compare: the same problem file, the same release, and the same score (the hidden tests, one run, pass or fail). Why only roughly: different models and agents, two of them with no agent loop at all; all three are marked "not independently verified" on the leaderboard; only one gives any cost figure; and the leaderboard's harness and dataset commits may differ from this project's pins (harness 8e894cf, dataset revision 5b807d9). Wilson intervals on their rows are computed here, from k and n. Source: LBC-bench, data file leaderboards.json at b835413.

The plain reading: Haiku 5.5 and gpt-6-luna inside this agent (52 to 56) land where two frontier models land in a single turn on the same problems (52 and 53), and near Claude Code with Sonnet 4.6 (48). With one run each and intervals about 20 points wide, none of these differences is established.

M3b's four arms (57.8% to 65.1% pooled pass@1), its confirming run, M3c's three arms and the Claude Code ladder (66.3% to 73.3%) are not drawn beside these rows: they were scored on 86 problems, the 92 minus 6 that no agent can reach, so their rates are higher by construction and do not sit on the same 92 as the LBC-bench rows. The LBC-bench row for Claude Code (Sonnet 4.6) is a different model and a different run from our ladder.
