CVDP RTL Agent: what passes the hidden testbench

IN ONE SENTENCE

What CVDP is

CVDP (Comprehensive Verilog Design Problems) is a hardware-design benchmark published by NVIDIA researchers in 2025: 783 problems in 13 categories when it was released. Each problem asks for RTL to be written, changed or fixed. The result is scored by a hidden testbench, usually a cocotb test, that the solver never sees.

What this project is

An open LangGraph agent, run end to end in GitHub Actions on the free, open-tool split of CVDP 1.1.0: 92 problems in four categories (spec to RTL 34, RTL modification 25, spec to RTL with module reuse 22, bug fixing 11). Every cost is provider-reported (via OpenRouter), every score comes from the hidden tests, and no LLM ever scores anything.

How it works

IN ONE SENTENCE

A six-node graph plans, edits, runs deterministic checks (compile, lint, synthesis, its own testbench) and decides whether to edit again or submit, under hard caps on turns, dollars and wall time, inside a Docker image that a GitHub Actions sweep runs on all 92 problems.

The graph is read_task → plan → edit → check → reflect → (edit | finalize). The LLM writes the plan, the edits and the decision. Everything else is code: the file tool writes only under rtl/, verif/ and docs/, and the checks are real tools (Icarus iverilog -g2012, verilator --lint-only -Wall, a Yosys read and synth, and a testbench the agent writes itself). The replay below is a long problem from the same run: nine turns, ending in a submit after the agent's own testbench had failed.

The sweep, as a schematic

sweep.yml · one dispatch = one model, one setting, one runnerGitHub Actions
Both images are built natively for x86-64 and Arm64 and pulled from GHCR. The harness runs 4 problems at a time. A shared ledger stops new problems calling the LLM once the summed cost passes the run budget. The work directory is uploaded only if a scan finds nothing key-shaped in it.

Stop rules, checked in code before every step

  • Turns: 10 edit, check and reflect cycles by default.
  • Dollars: $0.10 per problem, provider-reported cost only. A call whose cost is not reported stops the problem (cost_unreported), because the budget can no longer be enforced.
  • Wall time: 480 s, under the harness's 600 s agent timeout. Each LLM call has a hard deadline 2 s before the cap.
  • On any stop or crash, the last edit that compiled is kept, the summary is written, and the agent exits 0.
WHYWhy sweeps run in GitHub Actions, not locally

The CVDP harness needs a Docker daemon, and Actions has one on every runner, free for a public repository, with jobs of up to 6 hours. GitHub's runners come in x86-64 and Arm64, so every sweep can run natively on both with no emulation. Every run leaves a public run ID and a downloadable artifact (per-test logs, traces, summaries), so anyone can check a number against its run. And the heavy Docker work stays off the development machine.

WHYWhy the LLM never scores

Pass or fail comes only from the hidden tests the harness runs after the agent exits. A judge model can be argued with by the thing it judges, and its mistakes would be correlated with the agent's own, since they are the same kind of model. The failure labels are also made by deterministic rules (see the taxonomy), so no number on this page depends on a model's opinion.

WHYWhy cost is taken only from provider-reported usage

Price lists drift, and the provider that serves a call can charge a different price from the list: DeepSeek's calls went to 15 to 19 different providers per sweep. So the agent records the cost OpenRouter reports for each call, asks the generation endpoint if that is missing, and otherwise records null and stops the problem. Nothing is estimated. Where a cost is missing, every table shows a lower bound marked with ≥.

WHYWhy Wilson intervals, and why repeat runs

With 92 trials the normal approximation to a binomial interval is poor near 0% and 100% and can go outside [0, 1]; the Wilson score interval keeps its stated coverage at small n. But a Wilson interval only covers sampling over problems. It says nothing about the same problem coming out differently on a second run, which is why M2 ran every model twice and M3 measured the noise floor directly.

results.m36 ARMS

M3: six changes to the agent, none detectable

IN ONE SENTENCE

Turning the self-check or lint off, capping turns at 5 or 20, or cutting the budget to $0.02 changed the pass rate by less than two identical runs differ, though turning lint off made each solved problem 38 to 59% dearer.

Each arm is an ablation: one setting changed, everything else held. Every arm uses gpt-6-luna (the cheapest per solved problem in M2), all 92 problems, Arm64 and 4 threads, and runs twice. Each arm is compared with the base (A) problem by problem: a problem's rate in an arm is its passes over the arm's two runs, so 0, ½ or 1. The effect is the mean of the differences, with a paired bootstrap interval and an exact sign test.

paired effect on pass rate, points [95%] · against base Aband = noise floor, A2 vs A1

Intervals are from tools/ablate.py as committed in docs/reports/m3/arms_paired.md; the point effects and better / worse counts are recomputed from the CSVs by site/data/derive.py and agree.

F (20 turns) is the only arm worth a second look, ahead in both runs (62.0% and 58.7% against 57.6% and 55.4%). But only 6 of its 184 problem-runs used more than 10 turns, and 1 of those passed. The extra turns account for at most 1 of its 7 extra passes; the rest is noise.

Pareto · pooled pass rate against $ per problembars = 95% problem-bootstrap interval
The Pareto front is B, A and F, and its three points sit inside each other's intervals. The clear result is on cost: C and D are 33–55% dearer per problem. C's cost is a lower bound (one call unreported), so it is hollow and kept off the front.

What the agent did with its own testbench

problems where the agent ran its own testbench, of 92per run
With self-check on, the agent ran a testbench on only 31–32 problems. With lint off it ran one on 67, and the pass rate still did not move. Running its testbench more often does not help.
WHYWhy a paired bootstrap plus a sign test, not an unpaired comparison

Problems differ far more from each other than arms do: in M2, 29 problems passed every time and 28 never. An unpaired comparison of two pass rates puts all that between-problem spread into the error bar, and a 2-point effect disappears inside it. Pairing compares each problem with itself, so only within-problem change counts. The bootstrap resamples problems and keeps each problem's runs together, so it does not pretend the 184 problem-runs are independent. The exact sign test needs no distributional assumption at all: on the problems that changed, it asks whether "better" and "worse" are unbalanced.

WHYWhy the noise floor is measured on the same runner (A2 against A1)

An arm's effect means something only if it is bigger than the noise floor: the difference between two runs with nothing changed. Running the base twice on the same runner removes the runner as a cause. The result, −2.2 points [−8.7, +4.3] (3 better, 5 worse), is as wide as M2's Arm64 against x86 (−1.1 [−7.6, +5.4]), so the runner adds no noise of its own and 2 runs per arm resolve about ±5 points.

Why it fails

IN ONE SENTENCE

Of 565 failures, about half are hidden-test failures where the agent never ran a testbench, a quarter are interface mismatches with names the hidden testbench uses, and when the agent did test its own work, its testbench passed on code the hidden tests failed 61 times out of 73.

Every failed problem-run in M3's 14 runs gets one label: the first of a fixed list of rules that holds, read from the harness's per-test log, the agent's trace and its summary. The rules are in tools/taxonomy.py; no model is involved.

The interface story: a handle the agent was never given

Two labels are interface failures: the hidden build failed on code that compiled for the agent (74 failures, on 8 problems), or the hidden testbench reached for a port, signal, instance or parameter by a name the design does not have (73 failures, on 9 problems). The agent cannot see either from its own checks, because the names are only in the hidden testbench.

Self-check passed, hidden tests failed: 61 of 73

When a submission failed and the agent had run its own testbench on it, the last run of that testbench had passed in 61 of the 73 cases. Its testbenches check less than the hidden ones. These 61 failures are spread over 26 problems.

73 failed submissions with an own-testbench run · top: own testbench (blue = passed, ochre = failed) · bottom: hidden tests (hatched = failed)M3, 14 runs
Each pair is one failed problem-run: the upper segment is the agent's own testbench, the lower one the hidden tests.
WHYWhy deterministic rules plus hand labels, with a separate hold-out set

Rules give every failure exactly one label by a fixed precedence, from logs and traces, the same way every time, so anyone can rerun them on the committed CSVs. Hand labels check whether the rules say what a person reading the log would say. The rule-development set (15 real failures) found that the earlier rules missed name mismatches: they agreed on 12 of 15, the misses led to the signal_missing_hidden rule, and with it they agree on 15 of 15. Because that set shaped the rule, it cannot score it. So a hold-out set of 15 other failures was drawn after the rule was fixed (seed 20261024): 15 of 15 agree. It contains no signal_missing_hidden case, so the new rule is checked only on the development set, and the same person wrote both the labels and the rule.

Read as a verification engineer would

IN ONE SENTENCE

The agent's self-check is a testbench with no coverage and no quality measure, which is why it passed on code the hidden tests failed in 61 of 73 cases; the planned formal milestone answers that with a mutation-score gate on the agent's testbench and an interface diff by elaboration.

The hidden cocotb tests play the role of a sign-off regression the designer cannot see. The agent's own testbench plays the designer's unit test. Mapped onto the usual verification concepts, here is what the project does and does not do.

The two M3 failure modes have verification answers. A testbench that passes on wrong code is a testbench-quality and coverage problem: a mutation score asks whether the testbench fails on mutated copies of the design, and so measures what it can catch. A name the hidden testbench needs but the design lacks is an interface problem: elaborating the design and diffing its ports, parameters and hierarchy against the specification catches it before submission, when the name is given. Neither has results yet.

assert.validityLIMITS

Threats to validity: what this does not show

IN ONE SENTENCE

These results hold for one cheap model per ablation arm, on 92 open-tool problems, at a resolution of about ±5 points; they say nothing about smaller effects, other models, the heavy or commercial splits, or verification-writing tasks.

  • One model per arm. Every M3 arm uses gpt-6-luna. An ablation that does nothing for it may matter for another model.
  • Sampling is not seeded. CVDP_SEED is a label only; OpenRouter sampling cannot be seeded across providers. Both runs of every M3 arm carry the label seed 1.
  • The free, open-tool split only. 92 problems in four categories. The verification-writing categories (testbench stimulus, checkers, assertions: cid012–014) need Cadence Xcelium and are not run.
  • 2 runs per arm resolve about ±5 points. A real effect smaller than that would read as "no detectable effect". The null results are not evidence of no effect.
  • The hand-label hold-out had no signal_missing_hidden case, so the new rule is checked only on the set it was developed on, and the same person wrote the rules and the labels.
  • Problems are treated as exchangeable by the bootstrap and the sign test. cid003 (34 problems) weighs most.
  • Self-check pass or fail is read from truncated tool output in the trace.
  • The hidden build's own error text is not in the log, so a likely cause (a renamed or missing parameter on phase_rotation_0028) is not shown for each problem.
  • "Is the name given to the agent?" is a word search over prompt and context files. It cannot tell a signal from the same word in prose, and it is not yet a committed tool or done for compile_fail_hidden.
  • No per-category or AMBA effects. On the 8 AMBA problems every run passed 3 or 4; two runs give no power on 8 problems.
  • One run per runner in M2. The seeds measure the noise on 30 problems, not on 92, and the reasoning setting for each model was picked from one run on 10 problems.
  • The heavy split (75 problems) is not run with the agent. In 53 of them the hidden tests read files outside the agent's edit roots, and 3 (i2c 7, 46, 49) produced no test output even for the null agent.
  • Costs are lower bounds in two places: one unreported call in M2 (DeepSeek seeds) and one in M3 (arm C).
  • Caps are soft by design: wall time by up to about 40 s, the budget by up to one call.
  • Model serving varies: DeepSeek's calls went to 15–19 providers per sweep, so its cost and behaviour mix providers.
  • One log label is wrong but harmless: tools/log_check.py called a simulation that hung "harness_error" (4 in the first two M2 sweeps); the pass rates are right.

What's next

IN ONE SENTENCE

M3b, now being built, asks whether a different agent harness or a frozen lessons memory helps on the problems an agent can actually reach; a formal-methods milestone after it puts a mutation-score gate on the agent's testbench and an interface check in front of every submission.

M3b · IN PROGRESS

Four arms, same model and settings: A the current LangGraph graph; B the Deep Agents harness; C and D the same two with a frozen lessons memory. 3 runs per arm. Pre-registered primary effects: B − A and C − A.

The memory learns only from the 75-problem heavy split, then is frozen into a snapshot named by its content hash. At run time the agent gets the top 5 lessons by BM25 over the task text, with no model in the retrieval. The evaluation set is the 92 minus problems no agent can reach, by a pre-registered rule in tools/reachable.py. No results yet.

FORMAL · PLANNED

Two arms against the base on the M3b evaluation set, each a fixed step in the graph rather than a tool the LLM may skip:

  • a mutation-score gate: the agent's own testbench must fail on mutated copies of its design (Yosys mutate or MCY) before it may submit;
  • an interface diff by elaboration (pyslang or Yosys): the design's ports, parameters and hierarchy against the specification.

No results yet.

WHYWhy the evaluation set leaves out unreachable problems

If the hidden testbench needs a name that appears nowhere in what the agent is given, no change to the agent can make that problem pass. Keeping it adds only noise and shrinks every effect towards zero. So M3b fixes the rule before any scored run: a problem is unreachable when a handle its hidden testbench needs is given nowhere and M3 labelled it an interface failure in at least half of its 14 runs. The lists are committed first, and the effect on all 92 is still reported as a secondary table.

WHYWhy the lessons memory is frozen and learned only on the heavy split

A memory that has seen the evaluation problems' outcomes or traces can carry their answers into the test. That is leakage, and it would make any gain meaningless. So the memory learns only from the 75 heavy-split problems, which do not overlap the 92; it is frozen into one content-hashed snapshot; every result row names that hash; and the snapshot builder refuses, in code and under test, any work directory that contains an evaluation problem.
